## 板块一：系统目标与范围

本项目旨在设计并实现一套基于 Spring Boot + Vue3 前后端分离架构的图书借阅管理系统（LibMS），面向高校图书馆及中小型图书室的日常业务场景，将纸质台账与 Excel 管理模式升级为"图书档案—借书—还书—续借—罚金—统计分析"全流程数字化闭环，解决馆藏账实不符、借阅记录难追溯、逾期无人监督、馆藏结构无数据支撑四大业务痛点。为确保项目在 12 周开发周期内高质量交付，现明确系统业务边界如下：

**系统"做什么"（范围内）：**

1. 三类角色（系统管理员 / 图书管理员 / 读者）的登录认证与基于 RBAC 的权限控制；
2. 图书、分类、出版社等档案数据的增删改查与多条件分页检索；
3. 读者账号的生命周期管理（开户、检索、启用/停用、重置密码；删除仅经接口提供且设有护栏，页面不设入口）；
4. 借书、还书业务的事务化办理，含逾期天数计算与罚金登记；
5. 读者端图书检索、个人借阅查询、在线续借（每册限一次）；
6. 馆藏与借阅数据的统计总览（总量指标、月度趋势、分类占比、热度排行）。

**系统"不做什么"（范围外）：**

1. 不做移动端 APP、小程序及响应式移动适配（仅支持 PC 浏览器）；
2. 不做在线支付（罚金采取线下收取、系统登记模式）；
3. 不做短信 / 邮件推送（到期提醒通过「我的借阅」列表内逾期/临期高亮呈现）；
4. 不做图书预约、书评、推荐算法等社交化功能；
5. 不做高并发、分布式、全文检索引擎（Elasticsearch）等企业级架构；
6. 不做 ISBN 联网查重 / 第三方数据源对接（馆藏由管理员人工录入）。

## 板块三：核心业务流程设计

> 依据规划文档，选取**借书办理、还书办理、读者在线续借、预约排队**四个核心业务场景展开流程设计（四者构成借阅业务闭环；登录鉴权、档案 CRUD、统计查询、导入导出等流程已通过板块二用例覆盖，不在此重复展开）。

### 3.1 场景一：借书办理

**业务规则**：读者可借上限 5 册；借期 30 天；读者名下存在逾期未还或未缴罚金超过读者上限时禁止借书；库存扣减采用条件更新防超借；**同一读者同一本书在未归还前不得重复借阅（2026-10-23 起）**。

**① 前置条件与后置条件**

| 项目 | 内容 |
|------|------|
| 前置条件 | ① 操作者为图书管理员且已登录；② 读者账号状态为"正常"；③ 借阅证在有效期内；④ 同一读者同一本书未在借；⑤ 目标图书库存 > 0 |
| 后置条件 | ① `borrow_record` 新增一条状态为"借出"的记录（借出日期=当日，应还日期=当日+30 天）；② `book.stock` 减 1；③ 读者在借数量加 1 |

**② 主流程（正常路径）**

1. 图书管理员进入"借还办理"页面，选择"借书"标签；
2. 输入读者证号（或姓名模糊检索），系统返回读者信息及其在借数量；
3. 系统校验读者状态正常、借阅证在有效期内、在借数量 < 上限 5、名下无逾期未还、未缴罚金不超过读者上限、同一读者同一本书未在借；
4. 扫描 / 输入图书 ISBN，系统回显图书名称、作者、当前库存；
5. 管理员核对无误后点击"确认借出"；
6. 后端开启事务，执行条件更新：`UPDATE book SET stock = stock - 1 WHERE id = ? AND stock > 0`；
7. 判断受影响行数 = 1（扣减成功），插入借阅记录（借出日期 = 当日，应还日期 = 当日 + 30 天，状态 = 借出）；
8. 事务提交，接口返回成功；
9. 前端刷新读者在借数量与图书库存，提示"借书成功，应还日期为 ××××-××-××"。

**③ 分支 / 异常流程**

| 异常情况 | 处理方式 |
|----------|----------|
| 读者在借数量已达上限 5 册 | 第 3 步校验失败，终止流程并提示"该读者借阅数量已达上限，请先归还" |
| 图书库存不足（stock = 0） | 第 6 步条件更新受影响行数 = 0，事务回滚，提示"库存不足或已发生变化，请重试"；前端刷新库存 |
| 读者名下有逾期未还图书 / 未缴罚金 | 第 3 步校验失败，终止并提示"存在逾期未还或罚金未缴记录，请先处理" |
| 读者账号已冻结 / 注销 | 第 3 步校验失败，终止并提示"读者账号状态异常，无法办理借书" |

**④ 文字版流程图**

```
开始 → 管理员进入借书办理页 → 检索读者 → 判断[读者状态正常且无逾期且在借<5]
  ├─[否] → 提示具体原因 → 结束（借书失败）
  └─[是] → 扫描ISBN检索图书 → 显示图书与库存 → 确认借出
         → 开启事务 → 条件更新扣减库存 → 判断[受影响行数=1]
              ├─[否] → 事务回滚 → 提示"库存不足，请重试" → 结束（借书失败）
              └─[是] → 插入借阅记录（借出日期=当日，应还日期=+30天）→ 事务提交
                     → 刷新库存与在借数 → 提示借书成功 → 结束
```

### 3.2 场景二：还书办理（含逾期罚金）

**业务规则**：逾期天数 = 实际归还日期 − 应还日期（差值 > 0 判定为逾期）；罚金 = 逾期天数 × 0.5 元/天；罚金登记后由管理员线下收取并标记"已缴"。

**① 前置条件与后置条件**

| 项目 | 内容 |
|------|------|
| 前置条件 | ① 操作者为图书管理员且已登录；② 存在该读者状态为"借出"的借阅记录 |
| 后置条件 | ① 借阅记录状态更新为"已还"，归还日期 = 当日；② `book.stock` 加 1；③ 若逾期，`fine_record` 生成罚金记录（金额 = 逾期天数 × 0.5，状态 = 未缴） |

**② 主流程（正常路径）**

1. 图书管理员进入"借还办理"页面，选择"还书"标签；
2. 输入读者证号（或姓名模糊检索），系统列出该读者全部在借记录；
3. 每条记录显示书名、借出日期、应还日期，并由系统标注是否逾期及逾期天数；
4. 管理员选中待归还记录，点击"确认归还"；
5. 后端开启事务，更新借阅记录：状态 = 已还，归还日期 = 当日；
6. 系统计算逾期天数：`DATEDIFF(当日, 应还日期)`；
7. 判断逾期天数 ≤ 0（未逾期）→ 跳过罚金；图书库存加 1；事务提交；
8. 前端提示"还书成功"，在借列表刷新。

**③ 分支 / 异常流程**

| 异常情况 | 处理方式 |
|----------|----------|
| 该记录已归还（重复操作） | 第 4 步校验记录状态非"借出"，终止并提示"该图书已归还，请勿重复操作" |
| 归还时已逾期（逾期天数 > 0） | 第 6 步计算罚金金额 = 逾期天数 × 0.5 元，事务内一并写入 `fine_record`（状态 = 未缴），页面提示"本书逾期 N 天，应收罚金 M 元，请线下收取后在罚金管理中标记已缴" |
| 图书破损 / 遗失（人工判定） | 管理员终止正常还书，改走"赔偿登记"操作：手工录入赔偿金额写入 `fine_record`（备注破损 / 遗失），借阅记录状态更新为"已赔偿"，库存不恢复 |

**④ 文字版流程图**

```
开始 → 管理员进入还书办理页 → 检索读者在借记录 → 列出在借清单（标注逾期）
→ 选中记录点击归还 → 判断[记录状态=借出]
  ├─[否] → 提示"已归还，勿重复操作" → 结束（还书失败）
  └─[是] → 开启事务 → 更新记录（状态=已还，归还日期=当日）→ 计算逾期天数
         → 判断[逾期天数>0]
              ├─[是] → 生成罚金记录（金额=天数×0.5，状态=未缴）→ 图书库存+1 → 事务提交
              │      → 提示"还书成功，应收罚金 M 元" → 结束
              └─[否] → 图书库存+1 → 事务提交 → 提示"还书成功" → 结束
```

### 3.3 场景三：读者在线续借

**业务规则**：每册限续借 1 次；续借延长 30 天（自原应还日期起算）；已逾期记录不可续借；**有未缴罚金不可续借**；**该图书存在排队中/待取预约时不可续借**；仅允许操作本人记录（馆员可代办）。

**① 前置条件与后置条件**

| 项目 | 内容 |
|------|------|
| 前置条件 | ① 读者已登录（持有效 JWT）；② 存在本人状态为"借出"的记录；③ 该记录未逾期且续借次数为 0 |
| 后置条件 | ① 该借阅记录应还日期延长 30 天；② 续借次数置 1 |

**② 主流程（正常路径）**

1. 读者登录后进入"我的借阅"页面；
2. 系统列出本人全部在借记录，展示应还日期、剩余天数（剩余 < 7 天以高亮提示）；
3. 读者点击某记录的"续借"按钮；
4. 前端弹出确认框，展示续借规则说明（限一次、延长 30 天）；
5. 读者确认，接口携带 JWT 发起续借请求；
6. 后端校验（依据 Token 解析的用户 ID）：记录归属本人、状态 = 借出、未逾期、续借次数 = 0；
7. 校验通过，更新应还日期 = 原应还日期 + 30 天，续借次数 = 1；
8. 前端提示"续借成功，新应还日期为 ××××-××-××"，列表刷新。

**③ 分支 / 异常流程**

| 异常情况 | 处理方式 |
|----------|----------|
| 该记录已逾期 | 第 6 步校验失败，提示"本书已逾期，无法续借，请尽快归还并缴纳罚金" |
| 已续借过 1 次 | 第 6 步校验失败，提示"每册图书仅可续借一次" |
| 有未缴罚金 | 第 6 步校验失败，提示"请先缴清后再续借"（与借书"欠费禁借"规则联动） |
| 该图书已被预约 | 第 6 步校验失败，提示"该图书已有读者预约，无法续借，请按时归还"（避免队首被无限期拖延） |
| 越权访问（篡改请求中的记录 ID） | 后端比对记录归属人与 Token 用户 ID 不一致，返回 403（由全局异常处理器记录告警日志） |

**④ 文字版流程图**

```
开始 → 读者登录 → 进入"我的借阅" → 查看在借列表 → 点击[续借] → 确认续借弹窗
→ 携带JWT发起请求 → 判断[记录归属本人]
  ├─[否] → 返回403（告警日志） → 结束（续借被拒绝）
  └─[是] → 判断[状态=借出 且 未逾期 且 续借次数=0]
         ├─[否] → 提示具体原因（已逾期/已续借）→ 结束（续借失败）
         └─[是] → 更新应还日期(+30天)、续借次数=1 → 提示成功并刷新 → 结束
```

### 3.4 场景四：预约排队与到书取书（2026-10-22 新增）

**业务规则**：预约对有馆藏图书开放——有未被占用副本且无人排队时直接预留，否则按申请顺序排队（`queue_no` 递增）；还书后队首变为"待取书"，保留 7 天，逾期自动回收并顺延下一位；待取期间其他读者不得把该副本借走，待取读者借走后预约完成；被预约的图书禁止续借；同一读者最多同时保留 5 个有效预约。

**① 前置条件与后置条件**

| 项目 | 内容 |
|------|------|
| 前置条件 | 读者已登录（JWT）、账号正常；图书存在且未全部借出（仍有馆藏副本）；该读者未预约/未在借同一本书 |
| 后置条件 | `reservation` 新增一条"排队中"记录（分配 queue_no）；还书时队首变"待取书"（ready_time/expire_time = +7 天）；待取读者借书后变"已完成"；过期未取变"已过期"并顺延 |

**② 主流程（正常路径）**

1. 读者在"找书"页对有馆藏的图书点击"预约"；
2. 后端锁定图书行，按"无人排队且仍有未被占用副本"决定：是则直接预留（写入"待取书"并置 7 天截止时间），否则分配该书下一个 `queue_no` 写入"排队中"；
3. 图书归还时，后端在还书事务内把队首"排队中"提升为"待取书"，写入到书时间与 7 天截止时间；
4. 读者在"我的书架 → 预约"页签（侧边栏同时显示"N 本待取"）看到待取状态；
5. 读者到馆，馆员按正常借书流程办理；后端识别其为待取预约，优先放行并在借书成功后把预约置为"已完成"；
6. 若 7 天内未取，定时任务（每 5 分钟扫描）或管理员手动触发把预约置为"已过期"，并顺延下一位。

**③ 分支 / 异常流程**

| 异常情况 | 处理方式 |
|----------|----------|
| 图书有未被占用副本且无人排队 | 不再拒绝预约，直接转为"待取书"（相当于替读者把该副本预留，7 天内到馆取书） |
| 重复预约 / 已在借该书 | 拒绝并提示具体原因 |
| 队尾读者试图借走待取副本 | 拒绝："您前面还有 N 位预约读者"（待取/排队均计入前方人数） |
| 待取读者本人来借 | 放行；借书成功后预约置"已完成" |
| 无预约读者试图借走被待取占用的最后副本 | 拒绝："可借副本已被预约读者优先占用"（待取预约数 ≥ 可借数时） |
| 预约到期未取 | 定时任务/手动接口置"已过期"，队首顺延；库存口径不变（待取不扣 `book.stock`） |
| 读者被冻结/删除/改角色 | 自动取消其有效预约并顺延，避免白占队首 |
| 删除有有效预约的图书 | 拒绝删除，先处理预约 |

**④ 文字版流程图**

```
开始 → 读者找书（有馆藏）→ 预约 → 锁定图书行 → 校验[无重复预约且未在借]
  ├─[否] → 提示具体原因 → 结束
  └─[是] → 无人在排队且仍有未被占用副本？
         ├─[是] → 直接预留：写入"待取书"（含 7 天截止时间）→ 结束
         └─[否] → 分配 queue_no → 写入"排队中" → 结束
还书 → 库存+1 → 提升队首为"待取书"（7天）→ 读者到馆借书
  ├─[队首本人] → 放行 → 借书成功 → 预约"已完成"
  └─[他人/队尾] → 拒绝（预约优先）
7天未取 → 定时/手动回收 → "已过期" → 顺延下一位
```

> 实现口径：待取预约不扣 `book.stock`（库存仍是"可借册数"），借书时按"待取预约数"保护队首，因此巡检 R1"总册数 = 可借 + 在借 + 已赔偿"的口径保持不变；预约表自身的一致性由条件状态流转（排队中→待取→完成/取消/过期）与唯一索引 `(book_id, queue_no)` 保证。

## 数据表关联说明

本次输出的四个核心业务流程及其余用例对 9 张数据表的读写操作关联如下（R = 读，W = 写，C = 新增，U = 更新）：
> **2026-10-22 推荐项补充**：系统现共 **10 张表**，新增的 `notification`（站内通知/邮件 outbox）由"到书/到期/逾期/欠费/证将到期"提醒用例读写，不改变下表四个核心业务流程的读写关系；`sys_user` 新增的读者级额度字段（`borrow_limit`/`max_unpaid`/`valid_until`/`email`/`email_notify`）参与借书/续借/预约的规则校验，仍属同一批表。

| 业务场景 | 涉及数据表 | 读写操作说明 |
|----------|------------|--------------|
| 登录鉴权（公共） | `sys_user` | R：校验账号密码、读取角色，签发 JWT |
| **借书办理** | `sys_user` | R：校验读者状态、在借数量、逾期 / 罚金记录 |
| | `book` | R：校验库存；**U：条件更新扣减库存（`stock - 1`）** |
| | `borrow_record` | **C：插入借阅记录（借出日期、应还日期、状态 = 借出）** |
| **还书办理** | `borrow_record` | R：检索在借记录；**U：状态改"已还"、写入归还日期** |
| | `book` | U：库存加 1 |
| | `fine_record` | C：逾期时生成罚金记录（金额、状态 = 未缴）；W：线下收取后标记"已缴" |
| **读者续借** | `borrow_record` | R：校验归属 / 状态 / 次数 / 未缴罚金；U：应还日期 + 30 天、续借次数置 1 |
