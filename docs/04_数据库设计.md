## 一、数据库整体设计说明

本系统共设计 **10 张数据表**：`sys_user`（用户表，含读者与管理员）、`category`（图书分类表）、`publisher`（出版社表）、`book`（图书表）、`borrow_record`（借阅记录表）、`fine_record`（罚金记录表）、`notice`（公告表）、`operation_log`（操作日志表）、`reservation`（预约排队表，2026-10-22 刚需扩展新增）、`notification`（站内通知与邮件投递表，2026-10-22 推荐项扩展新增）。其中 `reservation` 与 `notification` 为扩展表，种子默认空且**均不设 `deleted` 列**（逻辑删除表仍为 5 张：`sys_user`/`category`/`publisher`/`book`/`notice`，巡检与答辩口径不变）。

各表之间的关联关系（文字版 ER 图）如下：

- **`book`** 作为馆藏核心，通过外键 `category_id` 关联**`category`**（多本图书属于一个分类，多对一），通过外键 `publisher_id` 关联**`publisher`**（多本图书属于一个出版社，多对一）；
- **`borrow_record`** 是业务流水中枢，一条借阅记录通过 `user_id` 关联**`sys_user`** 中角色为读者的记录（一个读者拥有多条借阅记录，一对多），同时通过 `book_id` 关联**`book`**（一本图书对应多条借阅记录，一对多）；`sys_user` 与 `book` 借此构成多对多关系，`borrow_record` 即为中间事实表；
- **`fine_record`** 通过 `user_id` 关联**`sys_user`**（一个读者可有多条罚金记录），通过 `borrow_id` 关联**`borrow_record`**（一条借阅记录最多因逾期产生一条罚金，破损/遗失赔偿亦挂靠该次借阅）；
- **`notice`** 通过 `publisher_id` 关联**`sys_user`**（管理员发布的公告，多对一）；
- **`operation_log`** 通过 `user_id` 弱关联**`sys_user`**（记录关键操作的操作人，允许为空以兼容无登录场景）；
- **`reservation`** 通过 `book_id` 关联**`book`**、通过 `user_id` 关联**`sys_user`**（一个读者可预约多本图书，一本书可有多位排队读者）；`(book_id, queue_no)` 唯一索引保证同书排队序号不重复，状态字段承载"排队中→待取书→已完成/已取消/已过期"的流转。
- **`notification`** 通过 `user_id` 关联**`sys_user`**（一个读者可收到多条站内通知/邮件，多对一）；`dedup_key` 唯一索引保证同一业务事件只提醒一次，表本身兼作邮件 outbox。

整体构成"档案域（category / publisher / book / sys_user）— 业务域（borrow_record / fine_record / reservation）— 辅助域（notice / operation_log / notification）"三个层次。

## 二、每张表的详细字段设计

> 命名规范：全小写 + 下划线；所有表以 `id` 作为自增主键；`create_time` / `update_time` 由数据库自动维护；档案类表含逻辑删除位 `deleted`（0 未删 / 1 已删），流水类表（借阅 / 罚金 / 日志）不删除、无该字段。
> 说明：用户被逻辑删除后，其历史借阅/罚金记录中的姓名与证号仍可回显（后端按 `selectUsersIgnoreDeleted` 自定义 SQL 忽略逻辑删除过滤，与图书历史书名回显口径一致）。

## 四、索引建议

> 说明：MySQL InnoDB 会为物理外键自动创建索引，故外键列无需重复建索引；以下列出全部业务索引（标注"建表内已含"者无需额外执行）。
> 唯一性约束（登录名、读者证号、分类名、出版社名、ISBN）采用「应用层校验 + 数据库生成列唯一索引」双重保障：
> 应用层先查后插给出友好提示；数据库层以生成列 `uk_*` 参与唯一索引，兜住并发竞态（原子性）。
> 生成列在 `deleted=1` 时取 NULL（NULL 不参与唯一约束），故逻辑删除后可复用同名/同号。

| 表 | 索引名 | 索引字段 | 类型 | 理由 |
|----|--------|----------|------|------|
| sys_user | uk_sys_user_username | uk_username（生成列） | 唯一 | 登录名未删除唯一，防并发重复（逻辑删除后释放） |
| sys_user | uk_sys_user_reader_no | uk_reader_no（生成列） | 唯一 | 读者证号未删除唯一（同上） |
| book | uk_book_isbn | uk_isbn（生成列） | 唯一 | ISBN 未删除唯一（同上） |
| category | uk_category_name | uk_name（生成列） | 唯一 | 分类名称未删除唯一（同上） |

## 五、表关联紧密性与事务一致性注意事项

**关联最紧密的表**：`sys_user` — `borrow_record` — `book` 三者构成系统业务金三角，一笔借书操作需同时触碰三张表（校验读者 `sys_user` → 条件更新扣减 `book.stock` → 插入 `borrow_record`）；其次为 `borrow_record` — `fine_record`（还书逾期时联动生成罚金）。开发中所有借阅业务代码应集中在这两条链路上进行充分的事务测试。

**事务一致性注意事项：**

1. **借书必须整事务提交**：`UPDATE book SET stock = stock - 1 WHERE id = ? AND stock > 0`（条件更新防超借）→ 判断受影响行数 → 插入 `borrow_record` → 条件更新 `sys_user.borrowed_count`（附加 `borrowed_count < 上限 5` 条件，并发下超额自增影响行数为 0、随事务整体回滚）；以上各步必须包裹在同一 `@Transactional` 方法内，任一步失败整体回滚；
2. **还书事务同理**：更新 `borrow_record`（状态/归还日期）→ `book.stock + 1` → 逾期时插入 `fine_record`，必须原子完成；
3. **冗余字段以流水表为准**：`book.stock`、`book.borrow_count`、`sys_user.borrowed_count` 均为冗余加速字段，事实源是 `borrow_record`；严禁在事务外单独修改冗余字段，避免账实不符；若出现不一致，以 `borrow_record` 聚合结果为对账基准修复；
4. **物理外键的连带影响**：外键 `ON DELETE RESTRICT` 会阻止删除被引用记录——删除分类/出版社前须确认无图书引用，删除图书前须确认无在借记录（历史已还 / 已赔偿记录不影响删除，业务上改为逻辑删除 `deleted = 1`），删除读者前须确认其借阅与罚金记录已结清；
5. **续借与逾期的边界**：续借校验（归属本人、状态在借、未逾期、`renew_count = 0`、无未缴罚金、图书无有效预约）与更新应在同一事务内以条件更新方式完成，防止并发重复续借突破一次上限；
6. **预约事务**：预约在锁定图书行后分配 `queue_no`（与借书/还书/编辑图书的图书行更新互斥）；还书时在同一事务内把队首提升为"待取书"；过期回收用 `WHERE status=2 AND expire_time < 参数` 条件更新，保证定时任务与手动触发并发时最多成功一次；待取不扣库存，避免破坏巡检 R1 口径。
