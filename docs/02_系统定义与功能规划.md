## 板块一：技术栈选型建议

### 后端层（backend/）

| 技术/框架 | 版本 | 选型理由（毕业设计角度） |
|-----------|------|--------------------------|
| JDK | Java 21（LTS） | 长期支持版，与 Spring Boot 3.x 匹配；已集成于现有工程 |
| Spring Boot | 3.2.5 | 自动装配 + 内嵌 Tomcat，开箱即用；3.x 是当前主流教程生态，答辩演示友好 |
| MyBatis-Plus | 3.5.5+（`mybatis-plus-spring-boot3-starter`） | 相比原生 MyBatis 免写基础 CRUD SQL；自带分页插件、条件构造器 `QueryWrapper`，是本系统"动态组合检索"难点的直接支撑（工程已采用 MP 专用 starter） |
| Maven | 3.8+ | 依赖管理与一键打包（`spring-boot-maven-plugin` 产出可运行 jar），部署答辩零环境依赖 |

| Lombok | 随 Boot 版本 | `@Data` 等注解消除实体类样板代码 |
| Bean Validation | starter 内置 | 入参校验（ISBN 格式、必填项、字段长度、金额/册数上限、新密码 6–20 位等，非法值返回 400 与字段级提示） |
| Knife4j | 4.4.0（可选） | 自动生成接口文档，答辩演示前后端契约、论文截图素材两用 |
| Hutool | 5.8.27 | 工具库（BCrypt 密码加密、JSON 处理等，工程已在用） |

| 技术/框架 | 版本 | 选型理由（毕业设计角度） |
|-----------|------|--------------------------|

## 板块二：系统定义与目标

**LibMS（图书借阅管理系统）** 是一套面向高校图书馆与中小型图书室的一体化 B/S 架构 Web 管理平台，核心价值在于把传统纸质台账或 Excel 管理图书的低效流程，升级为"借书—还书—续借—罚金—统计"全业务闭环的数字化系统：解决图书台账与实际馆藏不一致、借阅记录难追溯、逾期无人提醒、馆藏结构无数据支撑四大痛点。系统采用三角色权限模型：

| 角色 | 角色代号 | 权限描述 |
|------|----------|----------|
| **系统管理员** | ADMIN | 平台运维者：管理全部用户账号（读者开户/冻结、图书管理员分配）、维护基础数据（分类、出版社、借阅规则常量）、查看全局统计看板；不直接办理借还业务 |
| **图书管理员** | LIBRARIAN | 日常业务操作者：维护图书档案（增删改查、库存入库），办理借书、还书、续借，登记逾期罚金并在罚金管理中标记已缴，查询全部借阅流水 |
| **读者** | READER | 服务使用者：检索浏览图书，查看个人在借/历史记录，在线续借，查询个人逾期罚金，维护个人资料 |

数据规模预估：**9 张核心数据表**（用户、图书、分类、出版社、借阅记录、罚金记录、公告、操作日志、**预约**），符合 6–10 张的规划区间。`reservation` 为 2026-10-22 刚需扩展新增，种子默认空。
> **实际落地（2026-10-22 推荐项后）**：新增 `notification`（站内通知与邮件 outbox），共 **10 张表**，仍落在 6–10 张的规划区间内；`sys_user` 另按读者扩展 `borrow_limit`/`max_unpaid`/`valid_until`/`email`/`email_notify` 五个字段（表数不变）。

## 第三方服务的轻量替代方案

| 可能的第三方服务 | 本系统轻量替代 |
|------------------|----------------|
| 罚金在线支付（微信/支付宝） | 不接入：还书时系统**计算并登记应收罚金**，管理员线下收取后在系统中标记"已缴"，业务闭环完整且零成本 |
| 短信到期提醒 | 借阅列表**红色高亮**（"我的借阅"内标注"逾期 N 天"与临期"剩 X 天"） |
| 对象存储（OSS 图床） | 图书封面**本地磁盘存储** + Spring 静态资源映射 `/upload/**`（基础设施已预留，上传功能已裁剪） |
| 图书信息爬虫/ISBN 第三方查询 API | 管理员**手工录入**（Excel 批量导入已裁剪），规避版权与付费问题 |

> 结论：系统全部功能在本地技术栈内闭环，**不依赖任何付费 API 与外部服务**。

## 最大技术难点与风险点（结论）

本项目最大的技术难点集中在**借书/还书的多表事务一致性**——"校验读者额度与逾期状态 → 条件更新扣减库存 → 写入借阅记录"三步必须原子完成，其中防超借的条件更新写法、逾期罚金的边界计算（当天还算不算逾期）最考验细节，也是论文中最有分量的实现章节；最大的风险则是**时间风险**：开发后期与论文撰写期重叠，若前期数据库设计返工或前后端联调受阻，将连锁挤压收尾质量，因此必须坚守 MVP 边界——先保证借阅闭环 100% 可用，扩展功能按迭代五的实际进度宁缺毋滥，宁可功能少一项，不可核心流程带伤交付。
